## 适用

- 破解动作已跑通，进入交付与复盘阶段。
- 需要第三方只凭报告 + 证据目录就能复现补丁、keygen 或重打包结果。
- 需要回答“改了什么、为什么这么改、怎么验证、怎么退回去”。

## 执行顺序

1. 收证据：把 `evidence/` 命名、编号、补齐缺失输出。
2. 建 `report.md`，先写目标与环境，再写结论。
3. 写保护与关键发现，观察与推断分开。
4. 写破解路径：入口、补丁表、keygen、重签名或重打包。
5. 写验证矩阵，逐条挂证据编号。
6. 写回滚命令并实测。
7. 列交付物清单，逐个算 sha256。
8. 自检后交付；发现缺口加新证据条目，旧条目保持原样。

## 1. 报告结构

| 章节 | 必填内容 | 证据要求 |
| --- | --- | --- |
| 目标 | 文件名、版本、来源、原始 sha256 | E-001 |
| 环境 | 系统版本、架构、工具与版本 | E-002 |
| 指纹 | 文件类型、大小、依赖、架构 | E-003 |
| 保护 | 壳、混淆、反调试、签名校验、自校验 | E-004 起 |
| 关键发现 | 校验函数、分支、常量、协议 | 每条挂编号 |
| 破解路径 | 路线选择、补丁点、keygen 算法 | 补丁卡 + 脚本 |
| 验证 | 原版失败、补丁成功、负例、冷启动 | E-02x |
| 回滚 | 覆盖命令与校验 hash | 实测输出 |
| 附录 | 完整日志、脚本、已知限制 | 文件路径 |

结论先行：摘要里三句话写清“目标是什么、怎么破的、结果如何”。

## 2. 证据规范

- 编号 `E-001` 起连续，不跳号、不复用；删除的条目保留编号并标“作废”。
- 一条证据只回答一个问题，命令必须可复制执行。
- 每条含：命令、工作目录、输入 sha256、偏移或地址、输出片段、结论类型。
- 输出片段只贴决定性 3–10 行，完整输出留在 `evidence/E-0xx-*.txt`。
- 证据只追加不修改；写错了新增 `E-0xx（修正 E-0yy）`。

````markdown
### E-007 定位签名校验分支
- 命令: `rabin2 -zz sample/<BIN> | grep -i signature`
- 工作目录: `cases/<CASE>`
- 输入 sha256: `<HASH>`
- 偏移/地址: `0x100003f20`（文件偏移 `0x3f20`）
- 输出片段: `... signature check failed ...`
- 完整输出: `evidence/E-007-signature-strings.txt`
- 结论类型: 观察
````

## 3. 观察 / 推断 / 未知

| 类型 | 定义 | 写法 |
| --- | --- | --- |
| 观察 | 命令直接看到的事实 | “`0x3f20` 处为 `cbz w0`，见 E-007” |
| 推断 | 由观察推出、尚未单点验证 | “推断该分支控制试用期，依据 E-007、E-009” |
| 未知 | 没跑通或没覆盖 | “服务端二次校验未验证，阻塞点：无测试账号” |

规则：

- 推断必须引用观察编号，禁用“应该是”“大概率”。
- 未知写阻塞原因与下一步动作，禁用“后续再说”。
- 同一结论既有观察又有推断时，只把观察放结论，推断放分析节。

## 4. 复现步骤

按顺序写，每步三要素：工作目录、命令、期望输出。

1. `cd cases/<CASE>`；`shasum -a 256 sample/<BIN>`；期望等于 `<HASH>`。
2. 复制样本到 `patches/`；`cp -a sample/<BIN> patches/<BIN>`。
3. 执行补丁；`python3 patches/patch.py patches/<BIN> --offset <OFFSET> --expect <ORIG> --patch <PATCH_BYTE>`。
4. 重签或重打包；命令与第 6 节一致。
5. 跑验证矩阵；逐条记录输出。
6. 需要回滚时执行第 8 节命令，hash 回到 `<HASH>`。

复现步骤禁用“同前”“略”，每一步都要能单独粘贴执行。

## 5. 交付物清单

| 文件 | 说明 | 校验 |
| --- | --- | --- |
| `patches/<BIN>-patched` | 已打补丁并重签的产物 | sha256 + `codesign --verify` |
| `patches/patch.py` | 字节补丁脚本 | `--dry-run` 可复现 |
| `patches/offsets.json` | 偏移、原字节、补丁字节 | 与补丁卡一致 |
| `patches/rollback.sh` | 一键回滚 | 已实测 |
| `patches/keygen/` | keygen CLI 与样本输出 | 原版二进制验证通过 |
| `report.md` | 本报告 | 证据编号连续 |
| `evidence/` | 全部命令输出 | 只追加 |

交付前逐个算 hash，写进报告第 9 节；产物与报告放同一 case 目录。

## 6. 报告模板

````markdown
# <CASE> 破解报告

## 1. 摘要
- 目标: <SAMPLE>，sha256 `<HASH>`
- 路线: 静态补丁 / 动态 hook / keygen / 服务端模拟
- 结果: 补丁版通过验证矩阵，keygen 生成序列号被原版接受
- 交付: 补丁产物、补丁脚本、keygen、本报告

## 2. 目标与环境
| 项 | 值 |
| --- | --- |
| 目标文件 | `sample/<BIN>` |
| 版本 | `<VERSION>` |
| 架构 | arm64 / x86_64 / universal |
| 系统 | macOS `<VER>` / Windows `<VER>` / Android `<VER>` |
| 工具 | rabin2 `<VER>`、Frida `<VER>`、jadx `<VER>` |

## 3. 样本指纹
- 原始 sha256: `<HASH>`（E-001）
- 补丁产物 sha256: `<HASH>`（E-030）
- 文件类型/大小/依赖: 见 E-002、E-003

## 4. 保护与阻碍
| 保护 | 证据 | 处理 |
| --- | --- | --- |
| 加壳 | E-004 | upx -d / dump |
| 反调试 | E-005 | ptrace hook |
| 签名校验 | E-006 | 重签 + 补校验点 |

## 5. 关键发现
### 5.1 观察
- `<CHECK_FN>` 位于 `0x...`，返回 `Z`，1 为已授权（E-007）。
### 5.2 推断
- 推断该函数同时控制导出与打印，依据 E-007、E-011。
### 5.3 未知
- 服务端二次校验未覆盖，阻塞点：无可用测试账号。

## 6. 破解路径
### 6.1 入口
- 字符串 `...` → xref → `<CHECK_FN>`。
### 6.2 补丁
| 文件 | OFFSET | 原字节 | PATCH_BYTE | 语义 |
| --- | --- | --- | --- | --- |
| `<BIN>` | `0x<OFFSET>` | `<ORIG>` | `<PATCH>` | `cbz` → `b` |
### 6.3 keygen
- 算法: HMAC-SHA256 + Luhn 校验位；盐 `<SALT_HEX>`。
- 生成命令: `python3 keygen.py <NAME>`。
### 6.4 重签名 / 重打包
- `codesign --force --deep --sign - <APP>` 或 `zipalign` + `apksigner`。

## 7. 验证
| 用例 | 输入 | 结果 | 证据 |
| --- | --- | --- | --- |
| 原版 + 无效码 | `INVALID` | 失败 | E-020 |
| 补丁版 + 无效码 | `INVALID` | 成功 | E-021 |
| 补丁版 + 空输入 | 空串 | 不崩溃 | E-022 |
| 冷启动 | 重启 | 成功 | E-023 |
| keygen 抽样 20 条 | 生成码 | 20/20 成功 | E-024 |

## 8. 回滚
```bash
cp -a sample/<BIN> patches/<BIN>
codesign --force --deep --sign - <APP>
shasum -a 256 patches/<BIN>
```

## 9. 交付物
| 文件 | sha256 | 说明 |
| --- | --- | --- |
| `patches/<BIN>-patched` | `<HASH>` | 补丁产物 |
| `patches/patch.py` | `<HASH>` | 补丁脚本 |
| `patches/keygen/keygen.py` | `<HASH>` | 生成器 |

## 10. 附录
- 完整日志: `evidence/`（按 E 编号归档）
- 证据目录: `evidence/`
- 已知限制: 未覆盖服务端校验、未测试 ARMv7。
````

## 7. 报告自检

- 每条结论都有 E 编号，编号连续。
- 命令复制到终端能跑，不含“同上”“略”。
- 原始与产物 hash 都出现，且与实际文件一致。
- 验证矩阵至少包含原版失败、补丁成功、负例。
- 补丁卡字段与补丁脚本参数逐字一致。
- 回滚命令实测过，报告里的输出与 evidence 一致。
- 占位符只剩有意保留的 `<CASE>`、`<OFFSET>` 之类，没有漏填个人信息。
- 未知项写清阻塞点，不伪装成结论。

## 失败分支

- **证据缺失**：补跑命令重新采集，不凭记忆补写。
- **输出过长**：截取决定性片段，注明完整文件路径，避免整段粘贴。
- **多次运行结果不同**：记录时间、环境、随机因素，标注不可稳定复现。
- **报告与实测冲突**：以实测为准，新增更正条目，不覆盖旧证据。
- **补丁产物 hash 变化**：重签会改文件，报告里区分“补丁后 hash”与“重签后 hash”。
- **交付前发现新校验点**：在未知节标注未覆盖范围，不把部分结论写成全部。
- **路径含个人信息**：用 `<CASE>`、`<SAMPLE>` 占位，日志里同步替换。
